# 計算量（Big-O 記法）

同じ結果を得るアルゴリズムでも、データ量が増えたときの「遅くなり方」は大きく異なる。この「遅くなり方」を表すのが計算量（Big-O 記法）。

## なぜ計算量を考えるのか

敵が2〜3体しかいないゲームなら、当たり判定の書き方を工夫しなくても一瞬で終わる。しかし敵が1,000体になったとき、「全部の弾 × 全部の敵」を毎フレーム総当たりで比較するコードだと、一気に重くなることがある。計算量は、こうした「データが増えたときにどれくらい遅くなるか」を見積もるための考え方。

## Big-O 記法の読み方

`O(...)` の中に、データ数 `n` に対して処理回数がどう増えるかを書く。

| 記法 | 読み方 | 意味 |
| --- | --- | --- |
| `O(1)` | 定数時間 | データ数によらず一定の速さ |
| `O(log n)` | 対数時間 | データが倍になっても、処理回数は少ししか増えない |
| `O(n)` | 線形時間 | データ数に比例して処理回数が増える |
| `O(n²)` | 二乗時間 | データ数の2乗で処理回数が増える（増え方が急） |

## よく出てくる計算量

| 処理 | 計算量 | 備考 |
| --- | --- | --- |
| リストの `x in list` | `O(n)` | 先頭から順に探すため（[線形探索](01_algorithms.md#線形探索)） |
| 集合の `x in set` | `O(1)` | 集合は中身をハッシュ値で管理しているため速い（[集合（set）](../docs/python_grammar/01_basic.md#集合set)を参照） |
| リストの `append()` | `O(1)` | 末尾に追加するだけなので速い |
| リストの `insert(0, x)` | `O(n)` | 先頭に入れると、他の要素を1つずつ後ろにずらす必要がある |
| [二分探索](01_algorithms.md#二分探索) | `O(log n)` | 探索範囲を毎回半分にできるため速い |
| [選択ソート](01_algorithms.md#選択ソート) | `O(n²)` | すべての要素に対して、残り全部と比較するため |

> 「`in` で存在確認したいだけなら、リストより集合（set）の方が速い」というのは、実際にコードを書くときの判断材料になる。旧`022_frog_blaster`/`026_frog_blaster_sprite`（削除予定のため`bk/`へ退避済み）の `dead_enemies = set()` も、重複排除と存在確認を効率よく行う目的で集合が選ばれている、と捉え直せる。

## ゲームコードでの実例

「弾のリスト」と「敵のリスト」を総当たりで比較する当たり判定は、弾の数を `m`、敵の数を `n` とすると `O(n × m)` になる（旧`022_frog_blaster/game/gamecontrol.py`（`bk/`へ退避済み）の衝突判定がこの形）。

```python
for e in self.enemies:        # n 回
    for b in self.bullets:    # m 回
        if e.rect.colliderect(b.rect):
            ...
```

敵・弾の数がこのリポジトリのレッスンの規模（数十体程度）であれば全く問題にならないが、「なぜ大規模なゲームでは空間分割（マス目で区切って近くのものだけ比較する）のような工夫がされるのか」を理解する土台になる。
